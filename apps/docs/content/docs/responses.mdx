A response is one fill of a form. It stores a **definition snapshot** plus
answers.

<Callout>
  Submit validates the snapshot stored on the response, not the live
  questionnaire.
</Callout>

| Status      | Meaning                          | Mutations              |
| ----------- | -------------------------------- | ---------------------- |
| `draft`     | In progress                      | draft, submit, abandon |
| `submitted` | Locked after a successful submit | reopen, delete         |
| `abandoned` | Locked without submit            | reopen, delete         |

`reopenResponse` returns a submitted or abandoned row to `draft` without
rewriting the snapshot or answers.

---

## Lifecycle

<Flow
  label="Response lifecycle"
  steps={[
    { name: "start", kind: "protocol", note: "snapshot + defaults" },
    { name: "draft", kind: "client", note: "patch answers" },
    { name: "submit", kind: "server", note: "full replace" },
    { name: "reopen", kind: "data", note: "back to draft" },
  ]}
/>

1. **`startResponse`** — the form must be `active`. Copies the live definition, seeds `defaultValue`, status `draft`.
2. **`saveDraft`** — patch. A `null` value deletes a key. Empty required fields are allowed.
3. **`submitResponse`** — full replace, or omit `answers` to submit the stored draft. Required visible fields must be present.
4. **`abandonResponse`** — lock a draft without submit.
5. **`reopenResponse`** — unlock submitted / abandoned. `submittedAt` is left as stored.

Hidden `showWhen` fields are stripped on draft and submit. Unknown answer
keys are rejected.

## Endpoints

The browser client uses object args. `form.api` uses `{ query }` / `{ body }`.

| Client                                                 | Method | Path                |
| ------------------------------------------------------ | ------ | ------------------- |
| `startResponse({ formId, respondentId? })`             | POST   | `/response/start`   |
| `getResponse({ responseId })`                          | GET    | `/response`         |
| `listResponses({ formId?, status?, include?, … })`     | GET    | `/responses`        |
| `saveDraft({ responseId, answers, updatedAt? })`       | POST   | `/response/draft`   |
| `submitResponse({ responseId, answers?, updatedAt? })` | POST   | `/response/submit`  |
| `abandonResponse({ responseId, updatedAt? })`          | POST   | `/response/abandon` |
| `reopenResponse({ responseId, updatedAt? })`           | POST   | `/response/reopen`  |
| `deleteResponse({ responseId })`                       | POST   | `/response/delete`  |

`formId` on start is an id or slug.

`listResponses` defaults to summaries (no `answers` / `definition`).
Pass `include: "full"` for stored answers. Filter by `formId`,
`respondentId`, and `status`. The page is
`{ responses, limit, offset, nextOffset }`. Default `limit` is 50, max 100.

```ts
const page = await form.api.listResponses({
  query: { formId: "feedback", include: "full" },
});
```

## Optimistic concurrency

Optional `updatedAt` on draft, submit, abandon, and reopen must match the
stored row. A mismatch throws `STALE_UPDATE` (409).

Omit `updatedAt` to skip the check. `form.api` re-reads the row after
persist so the next token matches `get()`.

`useFormResponse` sends `updatedAt` and, on `STALE_UPDATE`, refreshes from
`getResponse`.

## Record shape

```ts
type ResponseRecord = {
  id: string;
  formId: string;
  status: "draft" | "submitted" | "abandoned";
  definition: FormSnapshot;
  answers: Record<string, unknown>;
  respondentId: string | null;
  submittedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
```

Set `respondentId` on start, or assign it in `onStart` before persist.
See [Hooks](/docs/hooks).
